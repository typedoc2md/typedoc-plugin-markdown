# Customization

You can extend the plugin beyond standard options, where possible integrating directly with the core TypeDoc API to ensure a consistent and predictable developer experience.

## Local Plugins

Plugins are the building blocks for extending the TypeDoc output.
Each plugin exports a load function that receives the resolved application instance as context.
See [Writing a TypeDoc Plugin](https://typedoc.org/documents/Development.Plugins.html) for more information.

```js filename="my-local-plugin.mjs"
// @ts-check
/**
 * @param {import('typedoc-plugin-markdown').MarkdownApplication} app
 */
export function load(app) {
  // do something with app instance
}
```

The plugin can then be consumed by adding the path to the plugin in your `typedoc.json` file:

```json filename="typedoc.json"
{
  "plugin": ["typedoc-plugin-markdown", "./my-local-plugin.mjs"]
}
```

Note plugins must be consumed as ESM.

<Callout type="important">
  `MarkdownApplication` is a type-only interface exported by this plugin. It
  allows local plugins to align TypeDoc's core `Application` typings with the
  runtime modifications introduced by this plugin.
</Callout>

## Hooks

Hooks allow strings to be injected into the output in specific locations and are the most basic form of customization.

They are based on the core [TypeDoc hooks](https://typedoc.org/documents/Development.Custom_Themes.html#hooks) implementation and exposed on a dedicated property to keep the API clearly plugin-owned.

```js filename="my-hooks-plugin.mjs"
// @ts-check
/**
 * @param {import('typedoc-plugin-markdown').MarkdownApplication} app
 */
export function load(app) {
  app.renderer.markdownHooks.on(
    'page.begin',
    () => `**Generated using "page.begin" hook**`,
  );
}
```

## Async Jobs

Async jobs are used to perform asynchronous tasks before or after rendering with a provided context.

They mirror the core [TypeDoc Async Jobs](https://typedoc.org/documents/Development.Custom_Themes.html#async-jobs) and are exposed via dedicated properties to keep the API clearly plugin-owned. Jobs are cleared after each render.

Each job function receives a single argument — the RendererEvent instance. Your IDE’s code intelligence (JSDoc and typings) will provide additional context and available properties.

```js filename="custom-plugin.mjs"
// @ts-check
/**
 * @param {import('typedoc-plugin-markdown').MarkdownApplication} app
 */
export function load(app) {
  app.renderer.preMarkdownRenderAsyncJobs.push(async (rendererEvent) => {
    await doSomethingAsync(rendererEvent);
  });

  app.renderer.postMarkdownRenderAsyncJobs.push(async (rendererEvent) => {
    await doSomethingAsync(rendererEvent);
  });
}
```

## Custom Theme

If there are some specific customization not achievable with hooks or events then a more advanced customization can be achieved by providing a new theme class which returns a different context class.

This implementation follows an adapted version of [TypeDoc's custom theming implementation](https://typedoc.org/documents/Development.Custom_Themes.html).

Please note that although the theme and router apis are public they are not covered by semantic versioning and the contract may change between versions (although changes will likely be minimal). If full stability is required please either fix versions, fork the project or do not extend them.

### Example

This code defines a new theme called “customTheme”:

```ts
export function load(app) {
  app.renderer.defineTheme('customTheme', MyMarkdownTheme);
}

class MyMarkdownTheme extends MarkdownTheme {}
```

The theme can then be consumed by the `theme` option:

```json filename="typedoc.json"
{
  "plugin": ["typedoc-plugin-markdown", "./local-plugins/my-custom-plugin.js"],
  "theme": "customTheme"
}
```

The themes can be extended to provide custom partials, helpers and templates by proving a custom render context class.

```ts
class MyMarkdownTheme extends MarkdownTheme {
  getRenderContext(page) {
    return new MyMarkdownThemeContext(this, page, this.application.options);
  }
}

class MyMarkdownThemeContext extends MarkdownThemeContext {
  // customise templates
  templates: MarkdownThemeContext['templates'] = {
    ...(this as MarkdownThemeContext).templates,
    reflection: (page) => {
      return `New template for ${page.model.name}!`;
    },
  };

  // customise partials
  partials: MarkdownThemeContext['partials'] = {
    ...(this as MarkdownThemeContext).partials,
    header: () => {
      return `
# Welcome to custom header for ${this.page.project.name} project!
Use my new helper - ${this.helpers.newHelper()}
`;
    },
  };

  // customise helpers
  helpers = {
    ...(this as MarkdownThemeContext).helpers,
    newHelper: () => {
      return 'New helper!';
    },
  };
}
```

Note the shape of the overrides:

- Spread via `(this as MarkdownThemeContext)` rather than plain `this`. The base class has already initialized these fields by the time the subclass initializers run, but TypeScript sees the subclass declaration as self-referential and reports `TS2729` without the cast.
- Annotating `templates` and `partials` gives each override's params their types from the base, so they do not need annotating individually. Leave `helpers` unannotated where the intention is to add new helpers to it.
- Each resource takes the params of the one it replaces. `templates.reflection` receives the page event (`page.model` is the reflection), while `partials.header` takes none and reads `this.page`.

Note also that, unlike TypeDoc's default theme, resources here are already bound to the context when they are created. Referencing `this` inside an override is safe, and so is detaching a resource from its namespace - `const { header } = this.partials` keeps working. Bound methods are not required.

### Markdown and utility functions

Templates, partials and helpers are written with a set of small pure functions, exposed so that a customized resource can reuse them rather than reimplement them. They are split into two namespaces:

- `markdown` - functions that emit markdown syntax, such as `link`, `heading` and `codeBlock`.
- `utils` - text transformations that do not themselves emit markdown, but prepare content to be embedded in it safely, such as `escapeChars`.

Both are reachable in two places - on the context as `this.markdown` and `this.utils`, for use inside a custom template, partial or helper, and as named exports from the package root, for use anywhere else (for example inside a hook or an async job, where there is no context).

```ts
import { i18n } from 'typedoc';

class MyMarkdownThemeContext extends MarkdownThemeContext {
  // a `sources` partial that omits the line number
  partials: MarkdownThemeContext['partials'] = {
    ...(this as MarkdownThemeContext).partials,
    sources: (model, options) => {
      const source = model.sources?.[0];
      if (!source) return '';
      const fileName = this.utils.escapeChars(source.fileName);
      const md = source.url
        ? this.markdown.link(fileName, source.url)
        : fileName;
      return options?.hideLabel ? md : `${i18n.theme_defined_in()}: ${md}`;
    },
  };
}
```

Reusing these matters more than the convenience. `escapeChars` in particular encodes which characters the plugin escapes, so a copy of it in a custom theme will silently diverge from the plugin's own output when that set changes.

The available functions are:

- `markdown` - `backTicks`, `bold`, `codeBlock`, `heading`, `horizontalRule`, `htmlTable`, `indentBlock`, `italic`, `link`, `strikeThrough`, `table`, `unorderedList`
- `utils` - `camelToTitleCase`, `encodeAngleBrackets`, `escapeChars`, `removeLineBreaks`, `unEscapeChars`

Note that unlike partials and helpers these are not bound to the context and take no `model` param. Utilities used internally by the plugin whose behaviour is tied to the render pipeline are deliberately not exposed.

Their signatures are stable, but their output follows the plugin's own formatting rules and may change between versions - which is the point of using them rather than copying them. The semantic versioning note above applies.

## Custom Router

The router determines which files are written and how links between them resolve. Eight are available, selected with the `router` option:

- `member` and `module` are provided by this plugin. `member` is the default, or `module` when `outputFileStrategy` is set to `modules`.
- `kind`, `kind-dir`, `structure`, `structure-dir`, `group` and `category` are TypeDoc's own routers, adapted to respect the plugin's file options.

Most routing requirements are met by choosing one of these. Where none fits, extend `MemberRouter` or `ModuleRouter` and override only the parts that differ, then register the result with `defineRouter`:

```js filename="my-router-plugin.mjs"
// @ts-check
import { ReflectionKind } from 'typedoc';
import { MemberRouter } from 'typedoc-plugin-markdown';

/**
 * @param {import('typedoc').Application} app
 */
export function load(app) {
  app.renderer.defineRouter('my-router', MyRouter);
}

class MyRouter extends MemberRouter {
  /**
   * @param {import('typedoc').Reflection} reflection
   */
  getIdealBaseName(reflection) {
    if (reflection.kind === ReflectionKind.Class) {
      return `classes-directory/${reflection.name}`;
    }
    return super.getIdealBaseName(reflection);
  }
}
```

The router is then selected by the name it was registered under:

```json filename="typedoc.json"
{
  "plugin": ["typedoc-plugin-markdown", "./my-router-plugin.mjs"],
  "router": "my-router"
}
```

Writing a router from scratch means implementing TypeDoc's [Router](https://typedoc.org/api/interfaces/Router.html) interface, which is beyond the scope of this guide. Extending one of the routers above is usually sufficient.

The semantic versioning note above applies to routers as well.
